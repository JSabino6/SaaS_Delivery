1) VISÃO GERAL DO SISTEMA
=================================================================

O projeto é um SaaS multi-tenant para restaurantes com atendimento via WhatsApp.
Cada restaurante opera de forma isolada, com configurações próprias, cardápio próprio, regras próprias e, agora, suporte a perfis operacionais por restaurante.

Objetivos do sistema:
- Receber mensagens do WhatsApp
- Entender intenção e itens do pedido com IA
- Validar preço, estoque, checkout e regras no backend
- Persistir estado de conversa e pedido
- Gerar Pix quando aplicável
- Exibir operação em tempo real no Dashboard
- Permitir gestão de cardápio, aliases, motoboys, perfis e regras estruturadas

Stack principal:
- Backend: FastAPI
- Frontend: Streamlit
- Banco: Supabase/Postgres
- Mensageria: Uazapi
- IA: Groq
- Cache e coordenação: Redis (opcional, recomendado)
- Pagamento: Mercado Pago

Princípio central da arquitetura:
- A IA interpreta o que o cliente quis dizer.
- O backend decide se aquilo é válido, calcula preço, reserva estoque e fecha o pedido.

- GET  /cron/avaliar

2.2 Camada de mensageria
Arquivo principal: API/zap.py

Responsabilidades:
- Recebe eventos do WhatsApp via webhook
- Valida segredos e limites de payload
- Extrai texto, mídia e metadados da conversa
- Faz debounce e agregação de mensagens curtas
- Usa Redis para deduplicação, lock e rate limit quando disponível
- Faz envio de mensagens e presença para Uazapi
- Encaminha o processamento final para o motor conversacional ativo

Motor ativo observado no código:
- zap.py importa e usa API/cerebro_v2_agente.py
- O arquivo API/cerebro.py ainda existe no repositório como legado e referência histórica, mas o fluxo principal atual usa o agente v2

2.3 Camada conversacional
Arquivo principal ativo: API/cerebro_v2_agente.py
Arquivo legado ainda presente: API/cerebro.py

Responsabilidades do agente v2:
- Define schema de tools para o LLM
- Monta prompt de sistema com personalização do restaurante
- Usa payload estruturado com pedido, estado, dados parciais e tenant_capabilities
- Executa tools de carrinho, FAQ e checkout
- Faz fallback defensivo quando a API da Groq devolve erro de validação de tool call
- Responde localmente alguns casos diretos, como resumo do pedido

Tools expostas ao modelo no v2:
- adicionar_ao_carrinho
- remover_do_carrinho
- atualizar_observacao
- solicitar_informacao_em_falta
- faq_query
- responder_faq
- avancar_para_checkout
- confirmar_dados_checkout
- finalizar_pedido

Características importantes do agente v2:
- Prompt estruturado por restaurante com blocos TOM DE VOZ, SAUDACAO, UPSELL, REGRAS POSITIVAS e REGRAS NEGATIVAS
- tenant_capabilities calculado por restaurante/perfil
- Proibição explícita de cálculo de preço, taxa, estoque ou desconto no modelo
- Slots de continuidade por estado: tamanho, borda, metades, seleções de produto, endereço, pagamento etc.
- Resumo de pedido tratado no backend sem depender da IA quando detectado

2.4 Camada de dados
Arquivo principal: API/banco.py

Responsabilidades:

2.5 Camada de utilidades

Responsabilidades:

- Centraliza variáveis de ambiente e guardrails
- Fornece helpers de normalização textual, formatação monetária e matching
- Abstrai Redis e execução bloqueante controlada
- Expõe configurações de debounce, rate limit, timeout e modelos

2.6 Dashboard administrativo
Arquivo principal: Dashboard/app.py

Responsabilidades:

3) MODELO MULTI-TENANT ATUAL
=================================================================

O projeto é multi-tenant em dois níveis:

Nível 1: restaurante
- Cada restaurante tem sua própria linha em restaurantes
- Cada restaurante tem seu phone_id, credenciais, configuração operacional e integração própria
- Produtos, bairros, pedidos, motoboys e entregas são vinculados por restaurante_id

Nível 2: perfis dentro do restaurante
- O projeto usa restaurante_perfis + restaurantes.perfil_ativo_id
- Um restaurante pode ter múltiplos perfis de operação
- O perfil ativo sobrescreve parte da configuração base do restaurante
- O cardápio e aliases podem ser escopados por perfil_id
- Novos pedidos persistem perfil_id e perfil_nome_snapshot

Campos com override por perfil observados no código:
- system_prompt
- regras_excecao_json
- bot_ativo
- mensagem_fechado
- taxa_entrega_padrao
- taxa_unica_ativa
- borda_gratis_automatica_ativa
- borda_gratis_padrao_nome
- endereco_loja
- telefone_loja
- horario_loja

Regra operacional importante:
- O backend sempre carrega o restaurante base, encontra o perfil ativo, faz merge dos overrides e só então monta o contexto final do tenant.

5) CARDÁPIO E REGRAS ESTRUTURADAS
=================================================================

5.1 Cardápio oficial
- O backend monta texto_para_ia, dict_precos, dict_estoque, dict_categorias e dict_aliases
- Esse cardápio é carregado já filtrado por perfil quando houver perfil ativo
- O preço oficial simples vem da tabela produtos

5.2 Estrutura inteligente do cardápio
O projeto evoluiu para um modelo mais robusto de regras estruturadas por tenant.
A configuração fica em regras_excecao_json e hoje pode ser editada visualmente no Dashboard.

Dois grupos principais de estrutura:

A) grupos_opcoes
- Serve para produtos compostos por grupo de escolha
- Exemplos: proteína, acompanhamentos, bebida, complementos
- Permite min, max e lista de opções válidas
- O backend usa isso para validar slot filling e pedir faltantes

B) secoes_configuraveis
- Serve para produtos com preço e composição mais avançados
- É o motor atual para produtos configuráveis multi-tenant
- Permite definir seções, tipos e políticas de precificação no backend

Tipos visuais já suportados no Dashboard:
- choice_single
- choice_multi
- variant_selector
- addon_group

Modos de preço já suportados no Dashboard/backend:
- sum_selected
- replace_base_price
- largest_selected
- fixed_delta
- no_charge

Exemplo de uso prático:
- Pizza Grande com seções sabores, borda, massa e adicionais
- O backend usa as opções cadastradas e calcula o preço final sem depender da IA

5.3 Local da gestão no Dashboard
No estado atual do projeto, a gestão visual dessa estrutura fica na área Gestão de Cardápio e não mais em Configurações.
Isso foi feito para alinhar a operação do restaurante: cardápio e lógica do cardápio no mesmo lugar.

8) PREÇO, ESTOQUE E REGRAS DE NEGÓCIO
=================================================================

8.1 Regra central
- O backend decide preço.
- A IA não calcula preço final, taxa, estoque ou desconto.

8.2 Preço simples
- Vem direto da tabela produtos

8.3 Preço configurável
- Vem de secoes_configuraveis em regras_excecao_json
- O backend valida escolhas e aplica a política de preço cadastrada
- O carrinho persiste pricing_context para auditoria

8.4 Estoque
- Atualizado por RPC segura movimentar_estoque_seguro
- O backend faz reserva/desreserva conforme mutações no carrinho

8.5 Meio a meio e produtos configuráveis
- O sistema já possui lógica de pizza meio a meio e foi evoluído para consultar regras configuráveis por tamanho quando existirem
- Quando o tenant configurar Pizza Grande, Pizza Média ou Pizza Pequena em secoes_configuraveis, o backend pode usar essa estrutura como fonte principal de preço

=================================================================
9) PAGAMENTO E CHECKOUT
=================================================================

Métodos atualmente tratados:
- Pix
- Dinheiro
- Cartão

Pix no projeto:
- Se pix_whatsapp_enabled estiver ativo e o token do Mercado Pago estiver válido, o backend pode gerar QR code e link
- O webhook do Mercado Pago confirma pagamento depois
- Se o tenant não tiver configuração pronta para QR no WhatsApp, o fluxo cai para Pix manual na entrega/retirada

Checkout flexível no v2:
- O cliente pode informar endereço e pagamento em qualquer ordem
- O bot pode iniciar checkout sem perder alteração de carrinho no meio
- O backend só finaliza quando dados mínimos estiverem completos

11) REDIS NO PROJETO
=================================================================

Quando Redis está disponível, o sistema usa:
- buffer de mensagens
- debounce de conversa
- deduplicação de eventos
- rate limiting
- locks distribuídos
- cache de dados do restaurante

Sem Redis:
- O sistema roda
- Existem fallbacks em memória para parte do buffer
- A robustez concorrente diminui

=================================================================

Práticas observadas no código:
- Segredos por variáveis de ambiente
- Token sensível criptografado com Fernet
