DOCUMENTAÇÃO COMPLETA DO CÓDIGO (PROJETO ATUAL)
Data: 2026-03-02

Esta é a documentação técnica do meu projeto de atendimento para delivery via WhatsApp.
Escrevi este material para facilitar manutenção, evolução e handoff sem depender de contexto externo.

=================================================================
1) VISÃO GERAL DO SISTEMA
=================================================================

Meu sistema é um SaaS multi-tenant para restaurantes.
Ele recebe mensagens do WhatsApp, interpreta pedido com IA, valida no backend, persiste no banco, gera Pix quando necessário e exibe operação no Dashboard.

Stack principal:
- Backend: FastAPI
- Frontend: Streamlit
- Banco: Supabase/Postgres
- Mensageria: Uazapi
- IA: Groq (chat e transcrição)
- Cache/concorrência: Redis (opcional, recomendado)

=================================================================
2) ESTRUTURA E RESPONSABILIDADE DE CADA ARQUIVO
=================================================================

2.1 API/main.py
- Inicializa FastAPI
- Executa startup diagnostics
- Aplica middleware de request_id e log de requisição
- Expõe rotas de webhook, cron, health e rotas administrativas

Rotas registradas:
- GET  /payments/qr/{payment_id}.png
- POST /webhook/mercadopago
- GET  /health
- POST /admin/cache/invalidate
- POST /admin/chat/toggle_pause
- GET  /cron/abandoned-carts
- GET  /cron/reset-states
- GET  /cron/avaliar
- POST /webhook

2.2 API/zap.py
- Recebe evento bruto do provedor
- Faz validação/autenticação do webhook
- Extrai texto, áudio e metadados de mensagem
- Aplica debounce e buffer por conversa
- Executa deduplicação e lock quando Redis está ativo
- Encaminha processamento final para a camada conversacional
- Faz envio de mensagens de saída para Uazapi

2.3 API/cerebro.py
- É o núcleo do motor conversacional
- Faz classificação de intenção (quando habilitado)
- Faz slot filling para extrair dados estruturados do pedido
- Aplica regras de negócio na evolução do checkout
- Valida regras de exceção do carrinho
- Gera respostas coerentes com estado e contexto
- Controla fluxos de pagamento/endereço/entrega

2.4 API/banco.py
- Centraliza acesso ao Supabase
- Busca dados de restaurante e cardápio estruturado
- Persiste pedido, estado de conversa e itens
- Atualiza estoque via RPC
- Implementa webhooks de pagamento e rotinas de cron
- Implementa healthcheck e utilitários administrativos

2.5 API/utils.py
- Carrega variáveis de ambiente
- Define guardrails de limite e timeout
- Fornece normalização textual e matching
- Encapsula helpers de Redis e execução bloqueante controlada
- Configura logger base da API

2.6 Dashboard/app.py
- Implementa login e perfil (admin, cliente, motoboy)
- Renderiza painel live de pedidos
- Permite gestão de cardápio/produtos/aliases/regras
- Permite configurações operacionais e integrações
- Exibe métricas e histórico

2.7 Arquivos de SQL na raiz
- Definem migrations e tabelas auxiliares para pedidos, pagamentos, motoboys, FAQ e entregas.

=================================================================
3) MODELO DE DADOS (RESUMO PRÁTICO)
=================================================================

Tabela restaurantes:
- Identidade do restaurante e configuração operacional
- Campos de integração (instance_name, instance_token, phone_id)
- Campos de IA e operação (system_prompt, bot_ativo, regras_excecao_json, etc.)
- Campos de Pix (pix_whatsapp_enabled, pix_provider, mp_access_token_enc)

Tabela produtos:
- Cardápio oficial por restaurante
- Preço, categoria, disponibilidade, estoque e aliases

Tabela bairros:
- Taxa de entrega por bairro (quando aplicável)

Tabela pedidos:
- Estado do pedido e dados do carrinho
- Campos de pagamento e confirmação

Tabelas conversas e clientes_estado:
- Histórico textual e estado da FSM por cliente

Tabelas motoboys e entregas:
- Controle da logística de entrega

=================================================================
4) FSM E FLUXO DE CONVERSA
=================================================================

O bot não trabalha como árvore fixa de menu.
Ele mantém estado de conversa e evolui de forma guiada por contexto.

Estados típicos de operação:
- INICIO (atendimento aberto)
- AGUARDANDO_ENDERECO
- AGUARDANDO_PAGAMENTO
- AGUARDANDO_PAGAMENTO_PIX
- AGUARDANDO_AVALIACAO_POS_VENDA

Princípio que eu adotei:
- A IA sugere entendimento
- O backend decide e valida

=================================================================
5) REGRAS DE NEGÓCIO IMPORTANTES
=================================================================

5.1 Preço e estoque
- O preço oficial sempre vem do banco.
- A IA não define valor final.
- Estoque é alterado via função segura no banco para evitar inconsistência.

5.2 Regras de exceção
- Uso JSON por restaurante para adaptar casos como:
  - limite de misturas em quentinha
  - restrição de combinações
  - regras de meio a meio
  - borda grátis em pizzaria

5.3 Aliases
- Produtos podem ter aliases para melhorar reconhecimento de linguagem natural.
- Isso reduz erro de interpretação por variação de escrita do cliente.

5.4 Pagamento Pix
- Se ativo, o pedido pode aguardar confirmação de pagamento antes da confirmação final.
- Webhook do Mercado Pago atualiza status de forma segura.

=================================================================
6) REDIS NO PROJETO
=================================================================

Quando Redis está ativo, ganho:
- Buffer/debounce robusto
- Deduplicação de evento (idempotência)
- Locks distribuídos (menos corrida em concorrência)
- Rate limiting por conversa
- Cache de dados de restaurante

Sem Redis o sistema roda, mas perde robustez em carga.

=================================================================
7) CRONS E AUTOMAÇÕES
=================================================================

7.1 /cron/abandoned-carts
- Envia lembrete e/ou encerra carrinho abandonado conforme janela configurada.

7.2 /cron/reset-states
- Limpa estados presos por inatividade.

7.3 /cron/avaliar
- Dispara pedido de avaliação após finalização.

Todos os endpoints de cron devem ser protegidos com CRON_SECRET.

=================================================================
8) SEGURANÇA E BOAS PRÁTICAS APLICADAS
=================================================================

- Segredos via ambiente
- Tokens sensíveis criptografados (Fernet)
- Verificação de webhook por segredo
- Guardrails de tamanho de payload e texto
- Middleware de request_id para rastreabilidade
- Logs por serviço (API e Dashboard)

=================================================================
9) COMO EU SUBO O AMBIENTE
=================================================================

9.1 Com Docker
- docker-compose up --build -d

9.2 Manual
Backend:
- cd API
- pip install -r requirements.txt
- uvicorn main:app --reload --host 0.0.0.0 --port 8000

Dashboard:
- cd Dashboard
- pip install -r requirements.txt
- streamlit run app.py
