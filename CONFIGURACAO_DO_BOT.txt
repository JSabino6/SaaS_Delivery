1) COMPONENTES QUE PRECISAM ESTAR RODANDO
=================================================================

1.1 Backend (FastAPI) - pasta API/
- Entrypoint: API/main.py
- Responsável por webhook, processamento conversacional, estoque, checkout, Pix, cron e utilitários administrativos

- Deduplicação de webhook
- Rate limit
- Locks distribuídos
- Cache de tenant

1.5 Uazapi
- Recebimento e envio de mensagens do WhatsApp

1.6 Groq
- LLM do agente conversacional
- Transcrição/normalização quando habilitado por configuração

1.7 Mercado Pago (opcional por tenant)
- Pix no WhatsApp quando habilitado

4) MULTI-TENANT E PERFIS
=================================================================

O sistema atual é multi-tenant por restaurante com suporte adicional a múltiplos perfis por restaurante.

Checklist de funcionamento:
- Cada restaurante precisa ter registro em restaurantes
- Se usar perfis, a tabela restaurante_perfis deve existir
- restaurantes.perfil_ativo_id deve apontar para o perfil atual quando houver perfis ativos
- Produtos e aliases podem ser escopados por perfil_id
- O backend mergeia o restaurante base com o perfil ativo antes de montar contexto operacional

Regra prática:
- Se houver perfil ativo, cardápio, aliases, prompt e regras podem variar por perfil.
- Se não houver perfil ativo, o sistema usa a configuração base do restaurante.

5) CONFIGURAÇÃO DO WHATSAPP (UAZAPI)
=================================================================

5.1 Recebimento
Configurar webhook do provedor apontando para:
- {PUBLIC_BASE_URL}/webhook?token={WEBHOOK_SECRET}

5.2 Envio
Cada tenant precisa ter no banco:
- instance_name
- instance_token
- phone_id

Sem esses três campos corretos:
- o backend não consegue identificar o tenant
- o envio de mensagens falha

5.3 Presença/typing
Se habilitado:
- UAZAPI_PRESENCE_ENABLED=1
- UAZAPI_PRESENCE_DELAY_MS ajusta o atraso de presença antes da resposta

6) CONFIGURAÇÃO DE PIX (MERCADO PAGO)
=================================================================

6.1 Pré-requisitos
- Token de acesso do Mercado Pago por restaurante/perfil operacional
- CRED_ENCRYPTION_KEY igual no Dashboard e na API

6.2 Fluxo atual
- O token é salvo criptografado em mp_access_token_enc
- O backend descriptografa quando necessário
- O tenant pode operar em modo Pix no WhatsApp ou fallback manual na entrega/retirada

6.3 Webhook Mercado Pago
Endpoint:
- POST /webhook/mercadopago

Validação:
- MP_WEBHOOK_TOKEN deve estar alinhado com o provedor

7) CARDÁPIO E ESTRUTURA INTELIGENTE
=================================================================

O sistema atual possui dois níveis de configuração de cardápio:

7.1 Cardápio base
- Tabela produtos
- Preço simples e oficial por item

7.2 Estrutura inteligente do cardápio
- Fica em regras_excecao_json
- É editada visualmente no Dashboard na área Gestão de Cardápio

Estruturas atuais suportadas:
- grupos_opcoes
- secoes_configuraveis

Tipos de seção configurável atualmente usados no editor visual:
- choice_single
- choice_multi
- variant_selector
- addon_group

Modos de preço observados no backend/editor:
- sum_selected
- replace_base_price
- largest_selected
- fixed_delta
- no_charge

Princípio operacional importante:
- A IA não calcula preço final.
- A estrutura inteligente do cardápio alimenta o backend, e o backend decide o preço.

=================================================================
8) PROMPT E PERSONALIZAÇÃO DO BOT
=================================================================

O prompt atual do restaurante/perfil é estruturado em blocos:
- TOM DE VOZ
- SAUDACAO
- UPSELL
- REGRAS POSITIVAS
- REGRAS NEGATIVAS

Esses blocos são montados pelo Dashboard e parseados pelo agente v2.

Recomendação operacional:
- Use REGRAS POSITIVAS para instruções obrigatórias de atendimento
- Use REGRAS NEGATIVAS para restrições comportamentais
- Não coloque regra de preço no prompt; preço deve ficar no banco e no backend

13) ERROS COMUNS QUE ESTE PROJETO COSTUMA SOFRER
=================================================================

- WEBHOOK_SECRET diferente entre provedor e backend
- PUBLIC_BASE_URL incorreta ou não pública
- CRED_ENCRYPTION_KEY diferente entre API e Dashboard
- instance_token vazio ou incorreto
- REDIS_URL inválida, derrubando robustez do debounce e dedup
- SQL de migração não aplicado, causando ausência de colunas/tabelas
- regras_excecao_json malformado
- perfil_ativo_id apontando para perfil inexistente
- configuração visual do cardápio não persistida no perfil/restaurante esperado
